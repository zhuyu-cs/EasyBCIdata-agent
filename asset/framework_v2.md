# EasyBCI-Data Agent — System Architecture (v2)

> Method-quality narrative supporting the system-architecture figure (Figure 1).
> Companion drawing prompt: `framework_v2_prompt.md`.

## Abstract

EasyBCI-Data is an LLM-driven multimodal neural-data preprocessing agent that converts a natural-language processing intent into a reproducible AI-ready mini-repository. The system is structured around four commitments that distinguish it from generic "LLM + tools" preprocessing assistants: (i) a strict **two-phase orchestration** in which an autonomous proposal phase is separated from an autonomous execution phase by exactly one human confirmation gate; (ii) a **four-layer hierarchical skill library** (L0 loaders / L1 orchestrator / L2 paradigm / L3 operator) dispatched on demand; (iii) **per-parameter evidence provenance** combining inspection statistics, web research, and registry defaults; and (iv) a **self-reinforcing flywheel** that crystallises successful runs back into the library, complemented by a parallel negative-example store and optional cross-lab federation. Raw neural recordings never enter the LLM context; only a textual *data fingerprint* does. The result is a system that can operate end-to-end on novel datasets while remaining auditable, reproducible, and bounded in both autonomy and failure modes.

## Figure 1 — System Architecture (caption)

EasyBCI-Data system architecture. Multimodal raw data (EEG / MEG / sEEG / ECoG / spike / fNIRS / …) stays locally guarded by a four-layer source-data guard; only a textual *data fingerprint* crosses into the agent. **Phase 1 (autonomous proposal)** chains light inspection → analysis-goal inference → deep inspection → proven-pipeline retrieval → evidence-driven planning, and ends at a single explicit human confirmation. **Phase 2 (autonomous execution)** generates a five-file standalone code bundle, runs it under a three-tier error-recovery loop with a hard retry cap, builds AI-ready segments, runs QC + visualisation, and exports a contract-enforced mini-repository. Successful specialised runs are crystallised into proven-pipeline skills; QC failures and user-flagged outcomes feed a parallel negative-example store. Both feed back as evidence for future runs and may be optionally signed (Ed25519) and federated across labs. ## Design Pillars

### P1. Two-Phase Orchestrator with a Single Human Gate

The orchestrator separates *proposal* from *execution* with a discipline that is uncommon in LLM agent systems: between data ingress and final mini-repo export, there is **exactly one** point at which the agent stops and waits for the human, and that point is fixed in advance (Step 7 of the orchestrator skill, after the proposal is fully composed). During Phase 1 Steps 0–6 the agent is forbidden from asking the user clarifying questions unless a structurally necessary field is genuinely unrecoverable from headers, channel count, sampling rate, filename, and domain-skill defaults. Phase 2 forbids any back-trip into Phase 1 except through a single bail-out condition — `recovery_exhausted=true`, triggered when the third consecutive autofix attempt on a stage still fails. The transition between phases is materialised on disk as a `proposal.confirmed` marker, and downstream tools (`generate_code`, `preprocess_neural`, `quality_check`, `export_repo`) refuse to run without it. This commitment is what makes the system *predictable*: a researcher who confirms the proposal knows that no further interruption, parameter revision, or scope drift will occur before the mini-repo lands on disk.

### P2. Layered Skill Hierarchy with On-Demand Dispatch

Domain knowledge is organised as a four-layer skill library and consulted strictly in the order **L1 → L2 → L3 → L0**. The L1 orchestrator (the master pipeline skill) is always loaded; the L2 paradigm skill (motor imagery, P300, SSVEP, sleep staging, sEEG epilepsy, connectivity, …) is fetched once modality + task are known; L3 atomic operators (notch, bandpass, ICA, CAR, ASR, drop-bads, threshold-spike, MUA binning, …) are fetched per-step to obtain parameter defaults and modality constraints; and L0 format loaders (NWB, BIDS-iEEG, MEF3, SpikeGLX, Open Ephys, Blackrock, Plexon, Neuralynx, SNIRF, LSL, …) are fetched only when the lightweight inspector cannot decode the file with built-in loaders. Inverting this order — fetching L3 operators before fixing the paradigm, or loading L0 loaders before the inspector has flagged a non-built-in format — would make parameter choices arbitrary and would waste turns; the strict ordering is what gives the agent a defensible reasoning trace in `plan/reasoning.md`.

### P3. Two-Stage Inspection Produces a Structured Fingerprint

Inspection is deliberately split. `inspect_data` is a light, header-only read (one-second sample): modality + channel summary + sampling rate + duration + event-table summary, used to choose the paradigm skill. `deep_inspect` is a full-data scan: per-channel variance / NaN / flat / spike statistics, Welch PSD with 50 / 60 Hz peak detection, sample-based artifact rate, bad-channel candidates, and a memory estimate. The deep report is written once to disk as a schema-versioned JSON (`middle_process/inspect/<file_id>/inspection_report.json`); every downstream tool re-reads from that single source of truth rather than re-parsing prose. The split exists because the light inspector is the input to *paradigm selection* (cheap, runs first), whereas the deep inspector is the input to *parameter selection* (expensive, runs once goal and paradigm are locked). For multi-input runs `deep_inspect` is invoked once per file and the results are appended to a routing table (see P6).

### P4. Per-Parameter Evidence Provenance

Each operator parameter in the staged proposal carries a `param_evidence` record with four fields: `source` ∈ {`inspection_report`, `research_parameter`, `empirical_default`}, `value`, `confidence` ∈ [0, 1], and `rationale`. The rationale must cite concrete numbers from the inspection report — "PSD peak at 50 Hz, 12 dB above neighbours" rather than "remove line noise". Rationale paragraphs follow an Observation / Strategy / Implementation structure with a minimum-word constraint, so that the audit trail cannot degenerate into single-line boilerplate. When a web-search provider is configured, `research_preprocessing` and `research_parameter` are invoked and their results are captured into `plan/web_evidence.json` together with provider, applied steps, confidence, and citations; when no provider is configured, the evidence record records `status="unavailable"` together with a diagnostic reason rather than papering over the gap. The user's final `plan/reasoning.md` is therefore a verbatim, per-step, per-parameter audit trail, not a generic post-hoc summary, and a citation-retraction sweep (`registry check`) keeps live web evidence reviewable.

### P5. Goal-Conditional Code Generation (Nine `analysis_goal`s)

A single registry defines nine `analysis_goal` values — `classification`, `source_localization`, `feature_extraction`, `clinical_screening`, `exploratory`, `generic`, `connectivity`, `phase_amplitude_coupling`, `online_inference` — and four code-generation flags per goal: whether the final `drop_nondata_channels:data_only` step is auto-injected, whether ICA is enabled, whether figures are produced, and whether epoched AI-ready outputs are built. The same registry gates eligibility for crystallisation into the proven-pipeline library. Two broad goals (`generic`, `exploratory`) explicitly opt out of AI-ready segmentation and crystallisation because they have no committed downstream purpose; `online_inference` opts out of figures and ICA for latency reasons; `connectivity` and `phase_amplitude_coupling` keep all channels and skip the data-only cleanup. Goal inference at Step 2 is itself defensive: when the user has not stated a downstream purpose, the agent defaults to `generic` rather than fabricating one, because false specialisation bakes a silent assumption into pipeline parameters that is much harder to undo than re-running with a specialised goal once the user clarifies.

### P6. Multi-Input Routing Table and Identity Resolution

For multi-session or multi-subject runs the orchestrator emits a single routing table (`middle_process/inputs_routing.json`) that maps each input file to a `(subject_id, session_id, stem_safe)` triple resolved by a deterministic chain: BIDS path → sibling BIDS sidecars → `participants.tsv` → manifest → same-directory heuristic. This table is the *only* source of identity downstream; the codegen layer ships a static safety check (`run_routing_safety_check`) that rejects generated scripts deriving `subject_id` from `Path(raw).stem`. Consequently a single canonical script per stage — `pipeline.py`, `qc.py`, `vis.py`, `build_ai_ready.py` — is written per `work_dir` and loops over the table internally. The "one pipeline reuses across all subjects/sessions" property is the whole point of the routing contract: a successful pipeline configured on one session generalises to every other entry without per-session script duplication, and a contract checker double-scans (forward and reverse) to guarantee that every routing entry receives outputs and every artefact traces back to an entry.

### P7. Three-Tier Adaptive Error Recovery with Bounded Retries

Phase-2 execution is wrapped in a recovery scheme with three escalating tiers: rule-based pattern repair (covering `import_error`, `attribute_error`, `value_error`, `shape_mismatch`, `dependency_missing`, `timeout`), memory match against the experience store of previously-fixed errors, and on-line web research for unfamiliar tracebacks. Each stage of Phase 2 has an independent autofix counter pinned to a hard cap of **three attempts**; the third failure raises `recovery_exhausted=true`, which is the *only* legitimate path from Phase 2 back to Phase 1. Failed artefacts — half-written `.nwb`, broken figures, corrupted reports — are quarantined under `middle_process/failed_outputs/<ts>/` or `middle_process/failed_qc/<ts>/` rather than overwritten in place, so the next retry never coexists with crash residue and the failed run remains forensically inspectable. Successful fixes are written back into the experience store, closing the loop on the second tier.

### P8. Mini-Repo Contract — Reproducibility by Default

Every run produces a five-directory mini-repository with a contract-enforced layout: `plan/` (proposal + reasoning + goal + web evidence), `code/` (five-script bundle — `pipeline.py`, `qc.py`, `vis.py`, `run.py`, `requirements.txt`, plus an optional `build_ai_ready.py`), `preprocessed_output/` (NWB-only `preprocessed/`, `.pkl` `AI_ready/`, `figures/`, and `QC_out/`), `middle_process/` (transient, removed only when both export and experience-save have succeeded), and a top-level `README.md` and `pipeline_record.json`. The `code/` bundle is **standalone**: it does not import `easybci_lib` and runs on any machine that satisfies `requirements.txt`. The final-output format is restricted to AI-ready, framework-agnostic extensions (`.nwb`, `.pkl`); vendor-native formats (`.fif`, `.set`, `.edf`, `.cnt`, `.vhdr`, `.nev`, `.smr`, …) are forbidden in the final layer and are swept to `middle_process/sweep_<ts>/` if found at the Step-12 pre-export self-check. The contract is the single source of truth — downstream skills, the proven-pipeline flywheel, and the reproducibility verifier all read this layout and not the LLM's narrative.

### P9. The Proven-Pipeline Flywheel + Negative Examples + Federation

Every specialised run that passes contract check is crystallised into an L1 proven-pipeline skill with a structured frontmatter (modality, paradigm, data profile, QC metrics, web evidence, source run, version) and a body composed of eight required sections — *When to Reuse*, *Data Profile*, *Pipeline Steps*, *Per-Step Rationale*, *Parameters Used*, *QC Result*, *When NOT to Reuse*, *References*. Retrieval uses a five-dimension similarity ranker — modality as a hard filter, paradigm / channel-count / sampling-frequency / duration as continuous dimensions, with cohort similarity as an opt-in sixth — composed with a *diversity penalty* (down-weighting repeated single-lab origins past a threshold) and a *negative penalty* (down-weighting matches whose `failed_step` set overlaps with the candidate). A parallel **negative-example store** records QC failures (auto-capture), user thumbs-down feedback, and CLI-flagged outcomes; relevant negatives are rendered into the system prompt as a "Known failure modes for similar data" block, capped at five entries, biased toward hard cases. Optional **federation** signs each skill body with an Ed25519 key, stores subscriptions under a TOFU public-key fingerprint, redacts cohort tags unless explicitly allowed, and pushes / pulls skill bundles through a `GitChannel` — turning the flywheel from a per-machine cache into a cross-lab knowledge graph that strengthens with every contributing site.

### P10. Zero Raw-Data Leakage

A four-layer source-data guard prevents the agent from observing or mutating user-provided recordings. The LLM's tool surface sees only the textual *data fingerprint* (modality, channel summary, PSD summary, artifact summary, fingerprint hash); the raw signal stays on disk under the user's filesystem, and every derived artefact is written into the mini-repo work directory. This property is what enables the system to be deployed in clinical, industrial, or otherwise sensitive environments where raw signal egress is prohibited — the agent's reasoning is portable while the data is not.

## End-to-End Walk-Through (Reuse Path)

A typical run on a 64-channel motor-imagery EEG session resolves as follows.

**Phase 1.** `inspect_data` reports 64 ch EEG at 512 Hz, 180 s, 14 events; analysis-goal inference reads the user's "train a motor-imagery classifier" phrase and emits `analysis_goal=classification`; `deep_inspect` reports two flat-channel candidates, a 50 Hz line-noise peak twelve decibels above its neighbours, and a stable PSD; `suggest_pipeline` retrieves the top proven match at similarity 0.71 with the analysis goal validated; in Reuse Mode the orchestrator copies steps and rationale verbatim from the matched skill; at Step 7 the human confirms with a single keystroke and `mark_proposal_confirmed` materialises `plan/proposal.json`, `plan/goal.json`, `plan/web_evidence.json`, and `plan/reasoning.md`.

**Phase 2.** `generate_code` writes the five-script bundle with the notch frequency fixed to the detected 50 Hz peak and an "Inspection-driven hints" comment block recording the bad-channel candidates; `preprocess_neural` runs `pipeline.py` once over the routing table; `save_processed` builds epoched `*_epochs.pkl`; `quality_check` runs `qc.py` and chains `vis.py` to produce five figures; `export_repo` assembles the mini-repo; Step 13 patches one row into the matched proven skill's *Reuse History* table rather than cloning it; Step 14 wipes `middle_process/`. Total agent turns: a small constant in the proven-match case, modestly higher in cold-start mode where Steps 5–6 invoke web research and Step 13 crystallises a new skill into the library.

## Notes for Figure Rendering

The diagram should privilege the *flow* (Phase 1 → gate → Phase 2 → mini-repo → flywheel) on the central axis, with the layered skill hierarchy and the three evidence sources as orthogonal sidebars feeding into Phase 1, and the negative-example loop together with federation as orthogonal sidebars feeding back from the mini-repo into the skill library. The single human confirmation gate must be visually distinct (a different shape and a contrasting accent colour) so that the reader identifies it at a glance — it is the architectural commitment, not a decorative detail. The mini-repo output should be drawn as a concrete directory tree rather than an abstract box, because the contract layout is itself a value proposition. Raw data should be visually walled off behind the source-data guard, with only the fingerprint shown crossing the boundary. The retry loop in Phase 2 should be drawn with an explicit "≤ 3" annotation on the back-arrow and a "recovery_exhausted → Phase 1" exit arrow, because the bound is the property — not the loop.
